🧠 **Assistant**

**SUDOKN's geospatial schema has been rebuilt on GeoSPARQL, and the old access path is gone twice over.** The 2026-06-19 version of this analysis reached coordinates by (a) *constructing* the site IRI as `company + '-geosite-1-instance'` and (b) reading `s:hasGeospatialLocation` → `s:hasLatitudeValue` / `s:hasLongitudeValue`. Both are dead:

- Site IRIs now end **`-geolocation-N-instance`**, and there is an explicit predicate, `s:organizationLocatedIn`, that links company to site — so the IRI never needed constructing.
- Coordinates are now standard GeoSPARQL: `geo:hasGeometry` → `geo:asWKT` carrying `POINT(lon lat)` literals. The custom lat/long predicates return nothing.

Both failures were silent — zero rows, no error — which is why the old transcript stopped working without anyone noticing.

**A structural change worth flagging.** The old `-geosite-1-instance` pattern assumed **one site per company**. SUDOKN now records **892 geolocations for 652 companies**, numbered `-geolocation-1-`, `-2-`, `-3-`… and some are plainly not U.S. plants (one company's geolocations include points in Dubai, Namibia and South Africa). Any analysis that silently took "site 1" is now taking an arbitrary one of several; the corrected query enumerates them all and lets the S2/county join decide which are in scope.

**Why the join is required.** SUDOKN has the manufacturer and its coordinates but no S2 cell; SAWGraph has PFAS samples keyed to S2 cells. There is no shared stored identifier and QLever offers no point-in-polygon, so the only route is to derive each site's S2 Level-13 cell from its point and match SAWGraph's cell.

**Join mechanics (computed crosswalk).** The `mcp-okn` `spatial_bridge` tool runs compute-and-inject: fetch `?site ?lat ?lng` (here parsed out of the WKT literal with a `REPLACE`), compute each point's Google S2 Level-13 `CellId`, format the spatialkg IRI `…/s2.level13.{id}`, inject the `(site, cell)` pairs as a `VALUES` block, and join `?cell` to a SAWGraph PFAS sample and to spatialkg's county. Nothing is persisted.

All six check out, one PFAS sample apiece. That closes the loop: the computed key is not merely plausible, it lands on cells that exist in the two target graphs.

**Why this answers the question — and what changed.** Six co-locations, against four in the 2026-06-19 run, and the geography has shifted: **Anoka County, Minnesota is new** (two shops, Molitor Polishing and Vision Coatings, in adjacent cells), as is Maricopa County, Arizona. Maine's Cumberland and York counties persist, reflecting SAWGraph's dense Maine PFAS sampling footprint. The Maine result is a sampling-coverage artefact as much as an industrial one — SAWGraph samples Maine far more heavily than most states, so absence elsewhere is not evidence of absence.

The co-location is a **screening signal, not an attribution**: sharing a 1 km cell says the plating shop and the PFAS detection are near each other, not that one caused the other. What makes it worth flagging is the prior — PFAS were used as chromium mist suppressants in chrome plating, which is why EPA treats NAICS 332813 as a point-source category for PFAS.
