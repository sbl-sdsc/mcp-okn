🧠 **Assistant**

The two Wikidata bridges reach ProKN's functional gene axis (`up:Gene` node, subject of `SIO_010078` 'encodes') from CFDE REVEAL's `geneToTrait` gene set very differently:

| Route into ProKN's functional gene axis | Wikidata property | ProKN functional genes reached |
|---|---|---|
| **Entrez → Ensembl** (crosswalk **C17**) | P351 → **P594** | **7,965** |
| Entrez → HGNC (crosswalk C13) | P351 → **P354** | **167** |

That is a **48× gap** — the HGNC route reaches ~2% of what the Ensembl route does — and it is structural, not incidental: ProKN's encodes/GO gene axis is **97.9% Ensembl** (8,148 of 8,325 `up:Gene` nodes) and only **2.1% HGNC-numeric** (177). The HGNC ids ProKN does carry sit mostly in OBJECT position on marker-gene / `biolink:target_for` / `seeAlso` statements — a different slice from the functional axis. So a gene / pathway / GO analysis of CFDE genes in ProKN must use the **Entrez→Ensembl (P594)** bridge (C17); the Entrez→HGNC route (C13) is correct only for that HGNC marker/target slice. Critically, the wrong route raises no error — the 167-gene join returns rows and looks like a successful result — which is exactly why C13 was mistaken for the pair's gene join. (Note: these `COUNT(DISTINCT)` figures compute cleanly server-side; but PULLING the ~7,965 matched gene rows for a local join is large enough that a client with a result-row cap can silently truncate the row set — pull each side as its own query and join in pandas.)
